# 소프트웨어 회사 업종 명세

문서 ID: BIZ-SW · 버전: 2.0 · 상태: MVP 구현 기준 · 기준일: 2026-11-11

[문서 트리](../README.md) · [업종 선택](README.md) · [소프트웨어 스토리보드](../03-experience/06-storyboard-software.md)

## 1. 플레이어의 역할

여러 고객이 공통으로 쓰는 제품을 개발하는 소프트웨어 회사를 운영한다. 어떤 문제를 해결할지 정하고, 기능 범위·품질 검증·출시 시점·고객 지원을 조절한다. 실제 코드를 타이핑하는 게임으로 만들지 않고 요구 카드, 작업 보드, 테스트 증거, 릴리스 승인으로 제품 개발을 체험한다.

대표 제품은 `SW_BOOKING_01` 예약 관리 앱이다. 카페·음식점의 예약 문제를 주제로 삼지만 MVP의 구매자는 NPC 업체이며, 다른 플레이어에게 앱을 팔거나 경쟁사의 고객 데이터를 가져오는 기능은 없다. **같은 제품 버전을 여러 고객에게 제공한다**는 점이 맞춤 계약을 수행하는 SI와 다르다.

## 2. MVP 구성

| 항목 | 범위 |
|---|---|
| 제품 | 예약 관리 앱 1개, 활성 안정 버전 1개, 검증 중 후보 버전 1개 |
| 초기 자산 | 기본 개발 보드·테스트 장비·상담석, 기초 앱 템플릿, 80 TC |
| 고객 | 패키지 소프트웨어 수요 NPC. 요구 기능·안정성·학습 난이도·도입 비용을 비교 |
| 거래 | 앱 도입과 초기 설정 1건. MVP에서는 자동 갱신 구독 없음 |
| 연구 | 안정성 / 사용성 |
| 사건 | 출시 범위와 일정 / 출시 후 오류 대응 |
| 설비 | `EQ_SW_1`, `EQ_SW_2`, `EQ_SW_3` |
| 후속 | 구독 청구, 자체 코드 입력, 실제 외부 서비스 연동, 플레이어 간 라이선스 거래 |

기본 거래는 매출 48 TC, 변동원가 18 TC, 고객 도입 작업 90초다. 원가는 도입·검증·지원 준비를 압축한 게임 자원이다. 이를 현실 소프트웨어의 복제 원가가 항상 일정하다는 경제 법칙으로 설명하지 않는다. 기본 거래 공헌이익은 30 TC이며 운영 고정비·연구비·사후 대응비를 제외하기 전 값이다.

## 3. 제품 개발과 판매를 분리한다

### 제품 버전 흐름

| 단계 | 플레이어 행동 | 남기는 증거 |
|---|---|---|
| 문제 확인 | 고객 요구 카드에서 목표 문제를 선택 | 목표 고객층·수용 기준 |
| 범위 설정 | 현재 버전의 해결 범위와 다음 버전의 범위를 구분 | 버전 요구 목록과 제외 항목 |
| 구현 계획 | 제공된 작업 카드의 의존 순서를 배치 | 작업 계획·선행 조건 |
| 검증 | 기능·회귀 테스트 카드를 실행하고 결함 원인을 확인 | 테스트 결과와 미해결 결함 |
| 승인 | 안정 출시 / 동의한 시험 고객에게만 제공 / 보류 | 릴리스 결정과 적용 대상 |
| 관찰 | 실제 사용 경험과 지원 요청을 확인 | 버전별 경험과 문제 원인 |

제품 후보를 만들었다고 바로 매출이나 명성을 지급하지 않는다. 매출은 고객 도입 거래가 완료될 때, 명성은 실제 관측된 고객 경험에 따라 반영한다. 연구·검증 과정을 건너뛰고 출시한 버전은 해당 위험 상태를 그대로 보존한다.

### 고객 도입 거래

수요 경쟁에서 고객이 업체를 선택하면 요구 확인 → 버전 제안 → 수락 → 초기 설정 → 인수 확인 → 완료를 진행한다. 원가와 필요한 운영비 예산을 수락 시 예약한다. 원가는 착수 시 소비하고 운영비는 실제 유상 운영 시간에 따라 소비한다. 고객에게 제안한 제품 버전과 조건을 거래에 고정한다. 작업 도중 새 버전이 나와도 동의 없이 기존 고객의 버전을 교체하지 않는다.

MVP는 자동 구독·해지·미납을 도입하지 않는다. 출시 후 오류는 버전과 영향 고객 집계를 참조하는 사건으로 다룬다. 무료 수정은 새 판매로 계산하지 않으며 동일 고객을 반복 지원한다고 완료 보상을 계속 만들지 않는다.

## 4. 품질과 R&D

| 축 | 관찰하는 문제 | 방치했을 때의 결과 | 회복 |
|---|---|---|---|
| 실제 품질 | 실패한 테스트, 알려진 결함, 검증되지 않은 변경 | 해당 조건에 노출된 고객의 오류·지원 경험 | 재현→수정 계획→검증→승인 |
| 시장 적합성 | 고객이 원하는 흐름을 제품이 지원하지 않음 | 구매 후보에서 낮은 적합성 | 요구 조사와 범위 조정 |
| 사용성 | 도입 절차가 길거나 안내가 불명확 | 도입·지원 만족도 하락 | 사용성 연구와 안내 검증 |
| 신선함 | 이미 익숙해진 출시 소식 | 새 소식의 주목 효과가 감소 | 실질적 변경이 있는 새 버전 발표 |

시간이 지났다는 이유만으로 안정된 소프트웨어의 코드가 자동으로 나빠지지는 않는다. 실제 결함, 변경된 요구, 명시된 환경 조건이 있을 때 영향을 적용한다. ‘최근 업데이트’ 배지만 바꾸어 결함이나 품질 기록을 초기화할 수 없다.

| 연구 ID | 완료 목표 | 선택의 비용 |
|---|---|---|
| `RND_SW_STABILITY` | 알려진 결함의 재현과 수정 검증, 회귀 확인 | 새 기능보다 안정성 작업에 슬롯 사용 |
| `RND_SW_USABILITY` | 목표 고객이 핵심 흐름을 이해하도록 개선 | 기능 수보다 접근성·학습 편의에 투자 |

각 단계는 20 TC와 활동 90초, 공유 생산 슬롯을 사용한다. 기존 고객 작업을 정리한 `CLOSED` 상태에서만 연구를 시작·진행하고 다음 확정 영업 약속과의 충돌을 검사한다. 최대 3단계이며 선행 사업 레벨 1·2·3이다. 정확한 품질 효과는 [운영과 연구](../01-game/03-operations-quality-rnd.md)의 수식을 따른다. 연구의 시각적 작업 카드는 별도 병렬 인력을 생성하지 않는다.

## 5. 선택 사건

### EV_SW_01 이번 버전에 어디까지 넣을까

조건: 목표 기능이 추가되었으나 약속한 출시까지 모든 검증을 끝내기 어려운 경우. 같은 원인으로 사건을 중복 생성하지 않는다.

NPC 대사: “새 기능은 반가워요. 우리 업무에 쓰려면 지금 제공되는 범위와 아직 시험 중인 범위를 알아야 해요.”

| 선택 | 릴리스 | 손익과 관계 |
|---|---|---|
| A. 검증된 범위로 안정 출시 | 통과한 기능만 포함 | 범위가 맞는 고객의 도입 가능, 추가 기능 수요는 놓칠 수 있음 |
| B. 동의한 고객에게 시험 제공 | 시험 표시와 제한된 대상 | 추가 관측을 얻지만 미해결 위험을 공개해야 함 |
| C. 출시 연기와 일정 재협의 | 후보 버전을 보류 | 검증 시간을 얻고, 확정 약속의 변경 동의가 필요 |

시험 제공에 동의하지 않은 고객은 안정 버전을 사용한다. 출시 연기를 눌렀다고 기존 계약의 날짜가 자동 연장되지 않는다. 실제 게임에서 코드를 생성하거나 외부 시스템을 변경하는 일은 없다.

### EV_SW_02 예약 저장 오류가 발견됐다

조건: 출시된 버전에 재현 가능한 결함이 있고 실제로 그 조건을 만난 고객이 존재한다. 서버 자체 오류와 제품의 게임상 결함을 구분한다.

| 선택 | 즉시 대응 | 후속 조건 |
|---|---|---|
| A. 검증된 이전 버전으로 복구 | 문제 버전의 새 도입 중단, 되돌릴 수 있는 기능만 복구 | 영향 고객 안내와 재검증 |
| B. 문제 기능을 제한하고 수정 | 나머지 검증된 기능만 제공 | 제한 조건 동의, 수정 테스트 통과 |
| C. 신규 도입을 잠시 멈추고 전체 점검 | 신규 매출 기회 포기 | 기존 고객 처리 계획과 재개 기준 충족 |

해결 버튼을 누른 즉시 명성을 복구하지 않는다. 결함 상태가 수정되고 고객 지원 결과가 확인된 뒤 이후 경험이 반영된다. 보상 비용을 제안할 때는 사용 가능한 TC를 먼저 확인하며, 돈이 없으면 무료 수정·제공 중지·다음 기회 회복의 대안을 제공한다.

### 사건 비용과 시간

| 사건·선택 | 추가 직접비 | 추가 작업 | 추가 운영비 예산 | 효과 |
|---|---:|---:|---:|---|
| EV_SW_01 A | 0 TC | 0초 | 0 TC | 검증된 범위의 안정 버전 유지·출시 |
| EV_SW_01 B | 0 TC | 0초 | 추가 고정분 없음 | 동의한 시험 대상에만 후보 버전 제공 |
| EV_SW_01 C | 0 TC | 검증 30초 | 1 TC | 고객 동의한 일정 변경과 추가 검증 |
| EV_SW_02 A | 0 TC | 0초 | 0 TC | 검증된 이전 버전으로 문제 노출 제한 |
| EV_SW_02 B | 0 TC | 수정 검증 30초 | 1 TC | 조건 재검증 후 문제 기능의 해결 여부 확정 |
| EV_SW_02 C | 0 TC | 0초 | 0 TC | 문제 버전의 신규 도입 중지, 미해결 결함 보존 |

추가 검증은 공통 슬롯의 `EVENT_WORK`로 수행하며 R&D 단계·XP를 지급하지 않는다. 1 TC는 추가 변동원가가 아니라 실제 운영 시간에 사용할 예산 예약이다. 예산이 없으면 A·C 등 추가 시간이 없는 대응을 남긴다. 고객 동의나 필수 검증이 필요한 경로는 선택만으로 통과하지 않는다. C의 판매 중지는 결함이 해결됐다는 뜻이 아니며 이후 수정 계획에 남는다. 수치의 권위는 [경제 원본](../01-game/06-economy-and-items.md)에 있다.

## 6. 설비와 공간

| 단계 | 설비 | 비용·선행 | 기능 |
|---|---|---|---|
| T1 | `EQ_SW_1` 기본 개발 작업대 | 시작 지급 | 기본 요구·작업·검증 흐름 |
| T2 | `EQ_SW_2` 검증 개발 작업대 | 120 TC, 레벨 2 | 결함 원인과 요구 추적을 지원 |
| T3 | `EQ_SW_3` 품질 개발 작업대 | 300 TC, 레벨 3 | 더 높은 품질 상한을 실현할 검증 도구 |

장비 구매만으로 개발 시간이 줄거나 고객 수가 늘어나지 않는다. 실제 작업과 검증이 품질을 만든다. 회사 공간의 간판, 상담석, 제품 시연대, 출시 기념품을 꾸밀 수 있다. 전시용 시연을 여러 번 실행해 매출을 만들지 않는다.

## 7. 저장·회복·교육

활성 버전, 후보 버전, 요구·검증 기록, 미해결 결함, 고객 동의, 지원 사건, 거래 조건을 저장한다. 후보 버전은 승인 전까지 공개 제품을 바꾸지 않는다. 재접속하면 동일 사건의 선택과 검증 결과를 이어간다.

결과 화면은 “테스트를 3번 눌렀다”보다 “어떤 고객의 어떤 요구를 충족했고, 어떤 위험을 남겼는가”를 보여준다. 교육 목표는 요구 이해, 범위 조정, 검증 증거, 사후 지원의 관계를 설명하는 것이다. 실제 프로그래밍 능력을 검증했다고 주장하지 않는다.
