# 콘텐츠 제작 규격

버전 2.0 · 설계 기준 2026-11-11 · 상태: 데이터 제작 기준안  
[문서 트리](../README.md) / [구현 문서](README.md)

## 1. 목적과 권위

콘텐츠 담당자가 업종·상품·연구·사건·선택지·튜토리얼을 추가할 때 게임 규칙과 정산을 우회하지 않도록 하는 규격이다. 장면 문구와 수치 파일을 따로 수정하다 서로 달라지지 않도록 원본을 지정한다.

| 콘텐츠 | 원본 문서 | 소비하는 곳 |
|---|---|---|
| 공통 가격·원가·연구비·운영비·아이템 | [경제와 아이템](../01-game/06-economy-and-items.md) | 지갑, 견적 UI, 균형 테스트 |
| 품질·공정·연구 효과 | [운영과 연구](../01-game/03-operations-quality-rnd.md) | 제품 상태, 고객 관측, 연구 UI |
| 수요·고객 효용 | [시장과 NPC](../01-game/02-market-and-npc.md) | 경쟁 배분, 시장 설명 |
| 업종별 작업과 사건 | [업종 문서](../02-businesses/README.md) | 작업 그래프, 사건 정의 |
| 카메라·연출·초기 도움 | [체험 문서](../03-experience/README.md) | 화면과 튜토리얼 |
| 상태·명령·기록 방식 | [공통 구현 명세](01-engine-neutral-spec.md) | 모든 콘텐츠 검증 |

서로 충돌하면 수치를 조용히 둘 중 하나로 선택하지 않는다. 변경 이유와 영향받는 장면을 기록하고 새 콘텐츠 버전을 만든다. 작업 중인 주문과 결정의 이전 버전은 완료까지 읽을 수 있어야 한다.

## 2. 업종 정의

`BusinessDefinition`은 `archetypeId`, `primaryProductId`, `workflowDefinitionId`, `startingAssets`, `researchBranches[2]`, `facilityTiers[3]`, `eventDefinitions[2]`, `demandNeedType`을 포함한다.

MVP 제품 키는 `CAFE_COFFEE_01`, `FOOD_RICE_01`, `SW_BOOKING_01`, `SI_RESERVATION_01`이다. 사건 키는 `EV_CAFE_01~02`, `EV_FOOD_01~02`, `EV_SW_01~02`, `EV_SI_01~02`다. 제품 이름은 현지화할 수 있지만 식별자는 바꾸지 않는다.

필수 설비의 functionBase가 소유되지 않았거나, 현재 배치에서 필수 사용점으로 갈 수 없으면 OPEN으로 전환하지 않는다. 유료 외형의 functionBase, 점유 영역, 접근점, 서비스 효과는 무료 대응 설비와 같아야 한다.

### MVP 예산 연습 정의

`ProjectDefinition`의 MVP 입력은 `PRJ_TRAINING_SETUP` 하나다. `mode=TRAINING_BUDGET`, PB 배정120, 공통 준비비60, 세 계약과 완료 증거를 정의한다. 이는 실제 상권 거래나 정식 공동 프로젝트가 아니다.

| 계약 | 추가 PB | 총 PB | 완료 증거 |
|---|---:|---:|---|
| A 직접 준비 | 40 | 100 | 준비 행동2단계 |
| B 준비 지원 | 60 | 120 | 준비 행동1단계 |
| C 단기 대여 | 50 | 110 | 준비와 종료 때 반납 확인 |

`pbSpent = fixedCostPB + optionCostPB`를 검사하고 120을 넘는 계약은 실행할 수 없다. 완료·취소 시 잔여 PB를 지우며 TC·DG·XP·아이템·명성을 지급하지 않는다. 최초 튜토리얼 전체 완료 XP20은 이 연습 보상과 별도 단회 조건이다. 세 계약의 행동은 같은 실행 규칙으로 검증하고 UI 클릭 로그만으로 완료시키지 않는다.

## 3. 작업 그래프

각 노드는 `nodeId`, `kind`, `requiredInput`, `durationActiveSeconds`, `latestCompletionActiveSeconds`, `allowedActions`, `nextNodeIds`, `onTimeoutPolicy`를 정의한다.

| 노드 종류 | 의미 | 검증 |
|---|---|---|
| Observe | 고객 요구·자료·상태 확인 | 확인 사실을 저장하되 무한 보상 없음 |
| Commit | 가격·범위·원가·운영비 예약 확정 | 예약 가능액과 약속 조건 표시 |
| Work | 제조·개발·설정 작업 | 슬롯 점유, 원가 소비 시점 한 번 |
| Verify | 맛·테스트·범위·검수 확인 | 결과가 실제 제품 상태에 연결 |
| Deliver | 납품 의도와 마지막 확인 | 이후 READY 자동 정산, 중복 매출 금지 |
| Recover | 재작업·취소·원가 복구 | 귀책과 복구 근거 ID 구분 |

분기마다 유한한 최대 경영 시간이 있어야 한다. 선택 대기 시간도 H 계산에 포함한다. 플레이어가 무한히 기다려 운영비 예약을 넘어갈 수 있는 노드는 배포하지 않는다. 기한이 있는 선택에는 시계가 진행하는 조건과 무응답 결과를 화면에 보여준다. 연결 복구·서버 장애 동안에는 이 기한도 정지한다.

## 4. 선택형 사건 정의

| 필드 | 규칙 |
|---|---|
| eventDefinitionId / version | 고정 식별자와 불변 정의 버전 |
| eligibility | 업종, 관측된 원인, 선행 결정, 제품 상태, 노출 조건 |
| category | 운영 문제·시장 변화·고객 요청 등. 반복 노출 통계 분리. |
| triggerEvidence | 왜 지금 발생했는지 설명 가능한 증거 키 |
| options | 보통 3개. 조건과 비용을 비교할 수 있는 행동. |
| immediateEffects | 등록된 비용·작업·약속 생성 요청. 임의 명령 문자열 금지. |
| delayedEffects | 조건·시계·effectId·최대 실행 횟수를 가진 후속 결과 |
| timeoutPolicy | 무응답 때 선택될 기본 행동과 손실 상한 |
| recoveryPaths | 부족한 자금·낮은 품질에서도 가능한 회복 행동 |
| summaryTemplate | 실제 선택·실제 결과·원인과 다음 시도에 대한 회고 |

선택지 카드에는 행동, 즉시 비용, 추가 운영비 예약, 걸리는 시간, 지킬 약속, 확실한 결과와 불확실한 결과를 구분해서 보여준다. 세 선택에 동일한 결말 문구만 붙이지 않는다. 후속 분기는 비용·시간·관계·제품 상태 중 적어도 한 가지를 바꿔야 한다.

### 검증 전용 예시

아래는 스키마 설명용 fixture이며 출시 사건 8개에 추가되는 콘텐츠가 아니다. 실제 값은 등록된 업무 정의에서 가져온다.

```json
{
  "eventDefinitionId": "FIXTURE_EVENT_ONLY",
  "version": 1,
  "eligibility": {
    "archetype": "CAFE",
    "observedCondition": "QUALITY_PROCESS_WARNING"
  },
  "options": [
    {
      "optionId": "OPT_REPAIR",
      "actionDefinitionId": "REGISTERED_MAINTENANCE_ACTION",
      "createsPromise": "VERIFY_BEFORE_REOPEN",
      "effectId": "VERIFY_RESULT_ONCE"
    }
  ],
  "timeoutPolicy": "REGISTERED_SAFE_CLOSE_POLICY"
}
```

이 fixture는 형식을 보여주므로 option 한 개만 있다. 출시 정의는 사용자에게 비교 가능한 실제 선택지를 제공해야 한다. 비용 숫자·보상·품질 변경을 모델이 이 payload에 임의로 추가하면 거부한다.

## 5. 사건 감독과 선택적 모델

기본 감독은 유효 후보를 만든 뒤 기록된 시드와 효용으로 선택한다. 같은 원인·후속 사건이 과도하게 반복되지 않도록 최근 이력, 쿨다운과 노출 한도를 적용한다. 어려운 상황을 더 악화시키는 사건은 등록된 회복 경로가 있는지 먼저 검사한다.

모델 입력에는 허용된 후보 ID, 현재 사건 맥락, 관측된 사업 상태 요약, 선택한 문장 스타일만 제공한다. 다른 플레이어의 지갑·개인 연구·결제 여부·인증 정보는 제외한다. 자유 문장인 간판·이름은 명령으로 취급하지 않는다.

모델 출력은 `candidateEventId`, `templateId`, 제한된 문장 변수와 제안 이유로 한정한다. 검증 후 실제 발생 결과와 사용한 모델·규칙 버전을 기록한다. 모델 응답을 기다리느라 스테이지 시뮬레이션을 멈추지 않는다. 문맥이 바뀌었거나 기한이 지났으면 제안을 버리고 이미 정한 기본 감독 결과를 사용한다.

모델이 꺼진 실행과 켜진 실행 모두 같은 핵심 콘텐츠와 회복 경로를 제공해야 한다. 모델 사용 여부를 경쟁 우위나 캐시 상품으로 만들지 않는다.

## 6. 아이템·개인화 제작 규칙

아이템은 `catalogId`, `functionBaseId`, `category`, `acquisition`, `currency`, `price`, `unlock`, `footprint`, `accessPoints`, `styleSlots`, `functionalModifiers`, `contentPhase`를 갖는다.

- 기능 항목은 TC·플레이 해금 경로를 가진다.
- DG 외형은 `functionalModifiers`가 비어 있거나 무료 대응 항목과 정확히 같다.
- 개인화는 승인된 템플릿·색·문양을 결합한다. 외부 코드나 실행 가능한 파일을 아이템으로 받지 않는다.
- 인스턴스에는 제작자, 획득 근거, 고유 ID를 보존한다. 외관이 같아도 소유권 기록을 공유하지 않는다.
- 회수와 재배치는 소유권 취소가 아니다. 환불·운영 정정에 의한 회수는 별도의 이유와 원장 근거를 가진다.

## 7. 콘텐츠 검증과 배포

| 단계 | 검사 | 실패 시 |
|---|---|---|
| 구조 | 필수 필드·유형·중복 ID·대상 참조 | 빌드 제외 |
| 그래프 | 도달 불가 노드·무한 반복·미정의 종료 | 배포 차단 |
| 경제 | 비용 범위·예약액·운영 시간·통화 분리 | 배포 차단 |
| 선택 | 무료 실행 가능한 경로·실제 결과 차이·지연 효과 단회 | 내용 수정 |
| 표현 | 원인 설명·정확한 가격·기한·용어 | 문구 수정 |
| 접근 | 클릭/터치 대안·키보드·색 이외 상태 표시 | UI 수정 |
| 재생 | 동일 fixture 결과·이전 버전 이어하기 | 호환 처리 또는 되돌림 |
| 운영 | 신규 생성 중지·기존 진행 완료 가능 | 배포 차단 |

가격 변경은 새 견적부터 적용하고 진행 중 계약을 바꾸지 않는다. 사건 중지 시 이미 확정된 선택을 삭제하지 않는다. 필요하면 중지 사유와 함께 무불이익 완료·비용 복구를 새 사건으로 기록한다.

## 8. 콘텐츠 완료 체크

업종 하나가 완료되려면 대표 제품1, 연구2갈래, 시설3tier, 사건2개, 개별 스토리보드10컷이 연결돼야 한다. 네 업종의 최초 플레이에 대해 ‘무엇을 관찰했는가 → 무엇을 결정했는가 → 어떤 결과가 남았는가’를 문서와 실제 로그에서 추적할 수 있어야 한다.

대사 수나 클릭 수만으로 교육 효과를 판정하지 않는다. [플레이테스트](../06-production/02-playtest-and-metrics.md)에서 처음 보는 상황에도 비용·시간·품질·약속을 비교하는지 확인한다.
