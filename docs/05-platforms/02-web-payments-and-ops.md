## 1. 재화와 결제의 관계

웹판은 실제 통화로 DG 디자인젬을 구매한다. TC는 게임 플레이로 얻고, PB는 프로젝트 예산이며, XP는 소비하지 않는 성장 값이다. DG는 외형과 배치 프리셋을 위한 재화다. 고객·명성·품질·연구 시간·생산 능력·사건 회피를 판매하지 않는다.

게임의 구매 기능과 실제 결제 활성화는 분리한다. MVP 테스트는 결제 sandbox와 테스트 지급으로 구현하고, 판매자 국가·출시 국가·대상 연령·결제 사업자 계약·통화·가격·환불 정책을 정한 뒤 실결제를 켠다. 이 미확정 사항은 네 업종의 무료 게임 구현을 막지 않는다.

### 첫 상품 구조

| 내부 상품 | 지급량 | 실화폐 표시 |
|---|---:|---|
| DG_PACK_100 | 100 DG | 공급자에 등록한 활성 가격·통화 |
| DG_PACK_250 | 250 DG | 공급자에 등록한 활성 가격·통화 |
| DG_PACK_500 | 500 DG | 공급자에 등록한 활성 가격·통화 |

묶음 수량은 초기 제안이며 판매 가격은 아직 확정하지 않았다. 실제 구매 화면은 서버가 확인한 product/price ID와 금액을 사용한다. 숫자를 임의로 환산해 표시하지 않는다. 특정 국가에서 특정 사업자를 사용할 수 있다고 가정하지 않는다. Stripe를 참조 구현 후보로 사용하되 실제 판매자 지원 조건을 확정한 후 채택한다. [P04]

## 2. PaymentProvider 인터페이스

| 동작 | 입력 | 출력·보장 |
|---|---|---|
| createCheckout | 내부 orderId, 승인된 packId, 계정, 가격 버전 | 외부 checkout ID와 호스팅된 결제 URL |
| verifyNotification | 원본 요청 본문과 서명·수신 문맥 | 검증된 외부 eventId 또는 거부 |
| fetchPayment | 외부 payment ID | 실제 결제 상태·금액·통화·상품·판매자 |
| normalizePaymentEvent | 검증된 외부 사실 | Paid, Pending, Failed, RefundUpdated, DisputeUpdated |
| requestRefund | 운영 권한·사유·검증된 구매 | 공급자의 환불 요청 ID와 현재 상태 |
| reconcile | 미해결 구매·정정 목록 | 누락 알림과 실제 공급자 상태의 비교 결과 |

카드번호·CVC를 게임 서버나 게임 화면에 직접 입력·저장하지 않는다. 결제 사업자의 호스팅 페이지로 이동하고, 돌아온 화면에서는 내부 주문 상태만 조회한다. 구매창 닫힘·성공 URL·클라이언트 메시지로 DG를 지급하지 않는다. Stripe 역시 landing page만을 완료 근거로 삼지 않고 webhook을 이용한 fulfillment를 요구한다. [P02]

## 3. 지급 흐름

1. 로그인된 사용자가 DG 팩을 선택한다.
2. 서버가 활성 카탈로그, 판매 가능 상태, 결제 계정 소유자를 확인하고 내부 구매를 만든다.
3. 같은 내부 구매 ID를 idempotency key로 공급자 checkout을 만든다.
4. 사용자가 호스팅된 결제 페이지에서 결제한다.
5. webhook endpoint가 원본 본문·서명을 검증하고 eventId를 durable inbox에 저장한다.
6. worker가 공급자 API로 필요한 상태를 확인하고 내부 주문의 상품·금액·통화·계정과 비교한다.
7. PAID가 확인되면 구매 기록·DG 증가·지급 lot·원장·outbox를 같은 DB transaction에서 저장한다.
8. 클라이언트가 현재 잔액과 지급 완료를 확인한다. 접속 중이 아니어도 지급 결과는 보존한다.

webhook은 durable inbox에 안전하게 들어간 뒤 빠르게 성공 응답하고, 복잡한 지급은 worker가 처리한다. 저장하지 못한 알림에 성공 응답하지 않는다. Stripe의 서명 확인에는 변경되지 않은 원본 본문과 공식 SDK 검증기를 사용한다. 중복 이벤트와 순서가 바뀐 도착을 허용하는 설계가 필요하다. [P01]

### 지급 중복 방지 키

eventId는 알림 중복을 막는다. `provider + providerPaymentId + grantKind`는 서로 다른 알림이 같은 지급을 일으키는 것을 막는다. `checkout.session.completed`와 다른 결제 완료 알림이 모두 와도 지급은 하나다. 결제가 아직 pending이면 DG를 미리 지급하지 않는다.

내부 구매 상태는 `CREATED → CHECKOUT_READY → PAYMENT_PENDING → PAID → GRANTED`로 진행한다. `FAILED`, `EXPIRED`는 미지급 종료이며 이미 지급한 구매의 뒤늦은 오래된 알림으로 GRANTED를 되돌리지 않는다. 공급자의 실제 현재 상태와 정정 사건을 구분해 처리한다.

## 4. 결제 기록과 권한

| 기록 | 필수 내용 |
|---|---|
| PurchaseOrder | 내부 주문·계정·팩·지급량·가격/통화·버전·공급자 ID |
| PaymentInbox | 공급자 eventId·종류·검증 결과·처리 상태·참조 ID |
| PaymentReceipt | 검증된 결제 ID·최종 상태·지급 operationKey |
| PremiumLot | 지급 구매·최초 DG·미사용 DG·정정된 DG |
| PremiumConsumption | DG를 쓴 아이템/프리셋과 어떤 lot에서 사용했는지 |
| Adjustment | 환불·분쟁 ID·누적 정정 목표·이미 반영한 값·근거 |

비밀키는 서버 비밀 저장소에만 둔다. 테스트 키와 운영 키를 분리하고, 공개 클라이언트 빌드에 포함되지 않는지 배포 검사한다. 관리자 정정은 역할·사유·상관 ID를 요구한다. 화면에서 accountId를 바꿔 다른 계정에 구매를 연결할 수 없게 한다.

## 5. 환불과 분쟁

환불 요청, 공급자 환불 성공, 카드 분쟁은 서로 다른 사건이다. 접수됐다는 이유만으로 환불이 이미 완료됐다고 표시하지 않는다. 공급자의 환불·분쟁 상태와 게임 권한 정정을 연결해 재처리할 수 있어야 한다. [P03][P05]

| 상황 | DG·외형 처리 | 보호할 것 |
|---|---|---|
| 지급 전 결제 취소 | 지급 없음, 구매 종료 | 미발생 지급을 되돌렸다는 허위 기록 금지 |
| 미사용 DG 전액 환불 확정 | 해당 lot의 미사용 DG 회수 | 다른 구매 lot·TC·XP 유지 |
| DG 일부 사용 후 환불 확정 | 구매 소비 추적에 따라 관련 외형 구매 정정 | 기능성 기본 설비·게임 진행 유지 |
| 부분 환불 | 누적 환불 비율로 회수 목표 계산, 이미 처리한 수량 제외 | 반올림 중복·다른 구매의 DG 침범 금지 |
| 분쟁 진행 중 | 관련 lot와 연관 권한에 제한 상태 표시 | 일반 게임 접속과 무료 진행 유지 |
| 분쟁 승소·취소 | 임시 제한만 해제 | 새 DG를 중복 발급하지 않음 |
| 분쟁 패소 확정 | 해당 구매 정정 목표에 반영 | 기존 환불과 같은 금액 이중 회수 금지 |

### 사용한 DG의 정정

MVP에는 사용자 간 거래·선물·상품 재판매가 없으므로 구매 원인을 추적할 수 있다. 회수할 lot의 미사용 DG만으로 정정 목표를 충족할 수 없으면 그 lot가 사용된 외형 구매를 필요한 범위에서 되돌린다. 아이템 구매 전체를 취소했다면 **그 구매에 사용한 모든 DG를 각각의 원래 lot로 먼저 복원하고, 각 원결제의 확인된 회수 목표에 해당하는 DG만 회수한다.** 다른 lot의 기여분뿐 아니라 같은 환불 대상 lot 안에서도 회수 목표를 초과하는 부분은 사용자에게 남아야 한다.

| 보존 예시 | 처리 | 최종 결과 |
|---|---|---|
| lot A의100 DG 전부로 아이템 구매 후 A에서10 DG만 정정 | 아이템 구매 취소로 A에100 복원, A의 회수 목표10만 차감 | 아이템0, A의 사용 가능 DG90 |
| 아이템100 DG를 A60+B40으로 구매 후 A에서10 DG만 정정 | 취소로 A60+B40 복원, A에서10만 차감 | 아이템0, A50+B40=90 DG |
| 첫 예시 처리 후 같은 원결제의 회수 목표가10에서20으로 증가 | 이미 취소한 아이템을 다시 취소하지 않고 A에서 추가10만 차감 | A80 DG, 누적 회수20 |

아이템 취소·lot별 복원·목표량 회수·정정 기록은 같은 DB transaction에서 확정한다. 아이템 구매 취소 키는 `itemPurchase/{itemPurchaseId}/reverse`, 각 lot 복원 키는 `itemPurchase/{itemPurchaseId}/restore/{lotId}`, 결제 정정 키는 `payment/{paymentId}/adjust/{normalizationRevision}`로 둔다. 같은 취소나 정정을 재전달해도 재복원·재회수하지 않는다. 이미 취소된 구매에서 새로운 복원 DG를 만들지 않는다.

적용 중이던 외형을 회수하면 대응 기본 외형으로 바꾼다. 프리셋 저장 권한을 회수해도 현재 배치나 기능성 가구를 지우지 않는다. 기존 프리셋 데이터는 보존하고 초과 슬롯의 편집을 제한하는 식으로 처리한다. 정정 후 DG를 음수로 만들어 상환 결제를 유도하지 않는다.

### 환불·분쟁 원금의 정규화

공급자 어댑터는 원결제별로 **중복 제거된 누적 실제 취소 원금** `confirmedCancelledPrincipalMinor`를 산출한다. 확정된 환불과 분쟁 손실의 원금 중 서로 겹치지 않는 부분을 합치고, 같은 원금에 대한 중복 알림·중첩 조정은 한 번만 포함한다. 공급자 수수료·분쟁 처리비는 사용자가 구매한 DG의 원금에 더하지 않는다.

각 근거에는 원결제 ID, 환불/분쟁 식별자, 확정 상태, 귀속 원금, 확인된 중첩 관계, `normalizationRevision`을 남긴다. 단순히 `refund + dispute`를 쓰거나 `max(refund, dispute)`를 쓰지 않는다. 중첩 관계가 불명확하면 이미 확인된 정정은 보존하고, 불확실한 추가 회수는 보류한 뒤 공급자 조회·조정 내역 대사 또는 운영 검토로 해결한다. 도착 순서나 이벤트 시각만으로 중첩 여부를 추정하지 않는다.

| 원결제 금액100의 사례 | 정규화한 실제 취소 원금 | 의미 |
|---|---:|---|
| 환불20 확정 후 남은80이 분쟁 패소 | 100 | 겹치지 않는20과80을 모두 반영. 단순 max인80은 잘못된 값. |
| 환불20과 동일 원금20을 다시 가리키는 조정 알림 | 20 | 같은 원금 두 번 회수 금지. |
| 환불20과 분쟁80의 귀속·중첩이 확인되지 않음 | 확인된20만 우선 유지 | 추가분은 조회·검토 전까지 보류. 임의80 또는100으로 확정하지 않음. |

단일 팩의 계산은 `targetDG = floor(originalGrantedDG × confirmedCancelledPrincipalMinor / originalPaidMinor)`다. 정규화 원금은0부터 원결제 원금까지이며, 원금 전부가 취소되면 지급 DG 전부를 목표로 한다. 세금·할인·여러 구매 항목이 섞인 결제는 해당 팩에 귀속되는 원금을 먼저 정규화한다. 실제 추가 회수량은 목표량에서 이미 순회수한 DG를 뺀 값이다. 이미 확정한 정정이 공급자의 후속 확정으로 취소되면 이전 정정에 연결한 반대 원장 기록으로 원래 lot에 복원하고 중복 발급하지 않는다.

## 6. 운영 화면과 알림

사용자 구매 내역은 팩, 지급 DG, 실결제 통화·금액, 지급 상태, 환불·제한 상태, 문의용 주문 번호를 보여준다. 지급이 늦으면 ‘처리 중’을 표시하고 재구매를 해결책으로 제안하지 않는다.

운영 화면에서는 지급 미완료 시간, 검증 실패, 금액 불일치, 중복 알림, 환불 정정 실패, 원장 불일치를 찾는다. 고유한 증빙 ID로 재처리하고 지급량을 직접 덮어쓰지 않는다. 판매 중지 플래그가 켜져도 이미 받은 돈의 지급과 환불 복구 worker는 계속 실행한다.

개인 메시지·간판·고객지원 입력은 화면에 안전하게 출력한다. 신고·차단·연령 및 국가별 접근 설정의 책임은 웹 운영자가 구현해야 한다. 목표 연령13+는 제품 기획 가정이며 특정 지역에서의 판매·접근 승인을 뜻하지 않는다. 실제 출시 국가와 사업자 조건을 정한 뒤 필요한 운영 정책을 확정한다.

## 7. 결제 공개 관문

- sandbox에서 성공·지연 성공·실패·중복·역순·재시작·환불·분쟁 시나리오를 실행한다.
- T18·T19와 공급자별 contract test의 원장 결과를 비교한다.
- 실제 상품 ID·가격·통화·지원 국가·판매자 계정·환불 정책을 확인한다.
- 비밀키·webhook 서명·origin·로그 노출·운영 권한을 확인한다.
- 기능 플래그로 신규 결제를 중지하고 기존 지급을 복구하는 훈련을 한다.

이 관문은 실제 유료 판매의 조건이다. 문서에 API와 상태도를 적었다는 이유로 결제가 검증됐다고 간주하지 않는다.

## 8. 공식 근거

확인일: 2026-11-11. 환불 시 게임 외형을 어떻게 정정할지는 오픈타운의 설계이며 공급자 문서의 의무를 그대로 옮긴 것이 아니다.

- [P01 — Stripe Webhooks](https://docs.stripe.com/webhooks): 서명 검증, 중복 이벤트, 도착 순서 비보장.
- [P02 — Stripe Checkout Fulfillment](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page): webhook 기반의 단회 지급과 비동기 완료.
